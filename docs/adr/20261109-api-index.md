# API index of the language as a release asset

- Authors: Phil Ewels
- Status: proposed
- Date: 2026-11-09

## Summary

Generate an API index of the Nextflow language from nf-lang, check its docs links against the live docs, and attach it to each release as `api-index.json`. Docs tools use it to link the names in code examples to the Nextflow docs.

## Problem statement

Docs sites link the names in Nextflow code examples to the Nextflow docs, with a card that shows the signature and a summary, much like a hover hint. The nf-core website does this with starlight-codeblocks. Its Nextflow adapter bundles a copy of the reference that a script scrapes from the docs source, so the copy goes stale between releases of the adapter, and the adapter carries Nextflow knowledge that belongs with Nextflow.

nf-lang already defines these names, with their types and descriptions, for hover hints. But it has no export for script definitions (`definitions.json` holds only the config scopes), and many of its `[Read more]` links are stale, for example `reference/process#cpus` for a directive.

## Goals

- One source for the names, types, and descriptions: nf-lang, as for hover hints.
- Docs links that work: each link checked against the live docs before a release.
- One index for each release, so that a docs site can link to the version that it documents.
- A format that is not specific to Nextflow, so that docs tools can read the indexes of other languages the same way.

## Non-goals

- Using the index in the language server.
- Replacing the plugin spec format or `definitions.json`.
- Publishing the index on a docs site or regenerating it on each commit.

## Considered options

### Keep scraping the docs in each docs tool

- Good, because the docs have the exact page and heading of each name.
- Bad, because each tool needs a Nextflow checkout and its own scraper, and its copy is only as current as its last release.

### Sphinx `objects.inv`

- Good, because it is a standard format that many tools read.
- Bad, because it has no signatures, summaries, or types, so a reader cannot resolve members (`fasta.baseName`) or show a card.

### Extend `definitions.json`

- Good, because it is generated already.
- Bad, because it is shaped for the language server (nested specs with parameter types), it has no docs links, and its plugin spec schema is published for plugins.

### API index as a release asset

- Good, because it comes from nf-lang and follows each release.
- Good, because its links are checked against the live docs before they are published.
- Bad, because `ApiIndexWriter` holds what nf-lang does not define (legacy operators, keywords, section labels) and the docs path of each kind of name, and these must follow the docs.

## Solution

The `buildApiIndex` task writes the index, `scripts/check-api-index.py` checks its links and writes the checked index, and the Bundle workflow attaches it to the release. See [API index](../api-index.md).

## Rationale & discussion

A release asset has a stable URL for each version and needs no docs site or commit, so the index changes only when a release changes it. The check runs on each push and pull request, so a docs change that breaks a link shows up before a release.

A name that the docs do not describe yet keeps a link to its page, and a name whose page is missing is dropped, so the index never publishes a broken link. The check fails only when many links break at once, which means that the docs moved.

The legacy operators in `ApiIndexWriter` could move to nf-lang as definitions with descriptions, and the stale `[Read more]` links in nf-lang could be fixed, so that hover hints link to the right pages too.
